# WILLIAMS BOT — Futures: исправление десятисимвольной вселенной и Long/Short

Дата: 2026-10-13  
Рабочая ветка: `futures-williams-campaign`  
Режим: Binance USDⓈ-M Futures Demo/Testnet; `DRY_RUN=true`, `ALLOW_LIVE=false`.  
Это журнал правок, не сертификат готовности к реальной торговле.

## Каноническая вселенная

Ровно 10 утверждённых USDⓈ-M USDT perpetual-контрактов, без подстановки по объёму:

1. BTCUSDT
2. ETHUSDT
3. BNBUSDT
4. SOLUSDT
5. XRPUSDT
6. DOGEUSDT
7. ADAUSDT
8. LINKUSDT
9. AVAXUSDT
10. LTCUSDT

Оба направления разрешены: LONG и SHORT. One-Way mode означает не более одной направленной позиции на символ одновременно; это не запрещает сканировать оба направления. Пять одновременно открытых кампаний остаются отдельным портфельным лимитом (`MAX_OPEN_POSITIONS=5`), а не размером вселенной.

## Исправления в коде

- `trading_config.py`: Futures-конфигурация не может молча подменить список через `WILLIAMS_SYMBOLS` или `AUTO_SCAN_SYMBOLS`; конфигурационный дрейф блокируется. H1 закреплён как таймфрейм решений, а структурная цепочка закреплена как D1/H4/H1/M15; неверные overrides блокируются.
- `futures_williams_runtime.py`: список берётся из единственного `DEFAULT_FUTURES_SYMBOLS`; проверяется ровно этот набор, статус сканирования содержит configured/evaluated counts; обе стороны рассматриваются независимо. Старые сигналы больше не выбираются раньше более новых, кандидаты ранжируются по score и свежести.
- `server.py`: исправлен счётчик сканера — он больше не полагается на отсутствующий атрибут `scanner.symbols`; API различает настроенные и реально проверенные пары, показывает LONG/SHORT candidate counts и сообщает BLOCKED/PARTIAL вместо ложного READY. Успешный скан без сигналов не маскируется под отсутствие кэша.
- `trading_config.py` и `futures_williams_runtime.py`: эффективные leverage/margin/one-way значения теперь проходят через валидированный конфиг, а не читаются независимо из сырого окружения. Leverage ограничен 2x, Futures требует ISOLATED и One-Way, дневной предел ограничен сверху 3%; статус API показывает эффективные, а не только заданные в environment значения.
- `.env.example`: удалён конфликтующий нижний `EXECUTION_TIMEFRAME=5m`; H1 остаётся единственным таймфреймом принятия решений. Dynamic/volume-based scan выключен.
- Android cockpit: устаревший список из пяти пар заменён на десять; карточка сканера показывает покрытие 10/10 и отдельные LONG/SHORT counts; READY без сигналов, BLOCKED и PARTIAL отображаются как разные состояния. Отдельно отображаются фактические разрешения LONG/SHORT, эффективное плечо, маржа и требование One-Way. Legacy native Spot runtime не объявляется авторитетным.
- `server.py`: устранён ещё один диагностический дефект — пустой список кандидатов при успешно проверенных десяти символах больше не выглядит как отсутствие кэша; PARTIAL/BLOCKED не маскируются под READY.
- `ci_release_gate.py`: добавлены статические проверки списка, обеих сторон, H1-цепочки, ограничений риска/маржи и диагностики.

## Добавленные регрессионные проверки

- Десять символов и оба направления проходят через сканер; направление-кандидат не теряется.
- Список с подменённым символом отклоняется до биржевого запроса.
- Неверные таймфреймы, CROSSED margin, отключённый One-Way и превышение 2x leverage обрабатываются по fail-closed/limit policy.
- Конфликт `WILLIAMS_SYMBOLS` / `AUTO_SCAN_SYMBOLS` отклоняется.
- Устаревший кандидат не получает приоритет перед более свежим/качественным.
- Булевы значения `1/true/yes/on` интерпретируются единообразно.
- Leverage выше 2x ограничивается; CROSSED margin и отключение One-Way отвергаются; дневной лимит не может превысить 3%; статус API отражает эффективные параметры.
- UI и API показывают число проверенных пар отдельно от числа LONG/SHORT кандидатов, поэтому «нет сигналов» не путается с «сканер не работал».

## Верификация и ограничения

Правки записаны в существующую ветку; `main` не менялся. На момент записи нет подтверждённого результата CI для финального SHA этой серии изменений, поэтому Python tests, release gate и Android lint/unit/build **не объявляются пройденными**. Нужны результаты workflow на точном HEAD и Demo fault/recovery-прогоны. Никакие реальные ордера не отправлялись.

Даже при зелёном CI это не доказывает прибыльность и не снимает release blockers по полной Futures lifecycle/recovery и Python/Android golden-vector parity.
