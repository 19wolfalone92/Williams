## 2. Найденные корни и каскады

### R01 — несовпадение канонических 15 контрактов с диагностическими проверками (подтверждён)

**Источник:** жёстко зашитые `10` в `CockpitDiagnostics.checks`, несмотря на `APPROVED_FUTURES_SYMBOLS.size = 15`.

**Последствия:** нормальные полные 15/15 котировки/индикаторы/H1/H4 показывались как `NOT_VERIFIED`, возникали ложные предупреждения в ZIP, триаже, UI и могли отвлекать от подлинной signed сверки.

**Исправлено в 4.64.12:** общее каноническое количество, проверка множества символов, регрессия «15 PASS, 14/duplicate NOT_VERIFIED». В торговую стратегию не вносилось новых разрешений.

### R02 — повторные SQL-записи неизменных signal timelines (подтверждено статическим трассированием)

**Источник:** `NativeFuturesCampaignCoordinator.saveIntents` вызывал наблюдателя на каждом durable intent commit; `WilliamsSignalJournal.orders` перебирал весь исторический журнал для каждого символа, повторно читал те же SQLite timeline и всегда делал `writeState` даже без нового события.

**Потенциальные последствия:** рост операций SQLite/CPU/аллокаций именно в критической фазе signed account-wide reconciliation; задержки STOP supervision и приватной синхронизации. **Это обоснованная причинная цепочка нагрузки, но сам по себе 14-секундный снимок не доказывает, что именно она вызвала прошлый OOM.**

**Исправлено в 4.64.13:** один индекс исторических владельцев по символам, одно чтение timeline на символ, запись только при добавлении события, корректная запись даже при ограничении ленты 256 записями. История фактических заявок, идентичность владельцев и fail-closed проверки не менялись. Отдельный тест доказывает отсутствие повторных записей для неизменных данных.

### R03 — лавина ложных fresh incident после перезапуска (подтверждено по ZIP и коду)

**Источник:** `TradingAuditStore.recordCampaignSnapshot` хранил отпечатки только в памяти. После процесса/обновления исторические `CLOSED_OR_STOPPED` и `EXIT_CONFIRMED` из durable journal ошибочно становились **новыми** `COCKPIT_EXECUTION`; старый терминальный `protection_status=SUBMISSION_UNKNOWN` создавал новый `COCKPIT_INCIDENT` без новой биржевой позиции.

**Последствия:** заполнение последних 1000 Cockpit-событий архивными событиями, запись больших исторических инцидентов, дополнительная нагрузка SQLite, некорректная приоритизация старой информации как новой.

**Исправлено в 4.64.13:** первый показ **подтверждённо терминальных** записей (включая `EXIT_CONFIRMED`) не создаёт нового UI-события. Последующие реальные изменения, незавершённые EXIT, активные неизвестные STOP и ошибки `FAIL` не подавляются. Исторические records остаются в SQLite, сами биржевые STOP продолжают проверяться подписанной сверкой.

### R04 — двойная сериализация durable intents на каждом сохранении (подтверждено кодом)

**Источник:** `saveIntents` дважды вызывал `array.toString()`: перед SQLite и при создании копии для observers.

**Последствия:** повторное создание строк на историческом длинном журнале, дополнительная нагрузка на Java heap и длительность critical reconcile.

**Исправлено в 4.64.13:** один неизменённый JSON `durableSnapshot` используется для durable write и **изолированной** копии `JSONArray(durableSnapshot)` для observer. Наблюдатель по-прежнему не может менять in-flight intents; его ошибка не может вызвать повторный ордер. Обновлён статический контракт `test_android_remote_only.py`.

### R05 — устаревший тест-план 10 рынков (подтверждено)

**Источник:** `TESTNET_RELEASE_GATE_RU.md` называл десять контрактов при 15 в native runtime.

**Последствия:** оператор мог проверить только десять пар и объявить неполную приёмку полной.

**Исправлено:** перечень 15 USDT perpetual и отдельное ограничение **не более 10 одновременно открытых кампаний**; обновлены P08/P10.

## 3. Что НЕ является доказанной ошибкой в этом ZIP

- `RECONCILE_REQUIRED` вместе с текущим `exchange_reconciliation_in_progress`: сохранение торгового шлюза закрытым **нужно** при несинхронизированных user WS и signed REST. Не убирать барьер ради зелёного индикатора.
- Пустой список `futures_exchange_stop_proofs.json` при нулевых позициях — это отсутствие тестового свидетельства, а не доказательство существования позиции без STOP.
- `HTTP 451` на hosted GitHub runner не означает, что тот же ответ возвращает Android: в ZIP телефон имел успешные public GET. Не обходить ограничение подменой live/Spot host.
- `OutOfMemoryError` и 4 CRASH из системной истории требуют повторного прогона на 4.64.13: один первый кадр `clockSnapshot` не доказывает, что он создал утечку памяти. Улучшения наблюдателя/сериализации уменьшают нагрузку, но не гарантируют отсутствие OOM.

## 4. Контракты, которые нельзя ослаблять

**Входы:** только TC2 H1, STOP-entry; TC1, NTD, Course не получают нового права выставлять ордер.  
**Внешняя биржа:** только Demo, signed `positions`/`open orders`/`algo STOP`; никакого автоматического live fallback.  
**Риск:** 15 сканируемых пар, 10 одновременных кампаний, совокупный риск не более 0,6%, дневной предел потерь 3%; торговля при несверенном аккаунте запрещена.  
**STOP:** хранение ID до отправки, signed доказательство соответствия направления, количества и уровня; неизвестный POST не может повторяться вслепую.  
**Реальная приёмка:** LONG/SHORT fills+protective STOP, сеть, reboot, update APK на физическом устройстве с сохранением ключей и точных signed receipts. Без этого релиз **HOLD**.
