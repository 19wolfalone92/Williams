# Williams 4.51.4 — сверка и защита Futures-позиций

Внешняя условная заявка могла остановить сверку раньше проверки SL уже открытой позиции. Исправление разделяет допуск новых входов и проверку защиты существующего риска.

## Изменения

1. Внешние заявки сохраняются в отдельном снимке. Они блокируют новые входы, но не обрывают аудит стопов открытых позиций.
2. Ручной SL проверяется по инструменту, направлению, активному статусу, биржевому идентификатору, типу `STOP_MARKET`, полному закрытию либо достаточному объёму `reduceOnly`. Уровень проверяется относительно соответствующего `MARK_PRICE` или `CONTRACT_PRICE`. Проверка защиты не присваивает ручную позицию стратегии и не разрешает автоматически менять ручной стоп.
3. При неподтверждённой полной защите подтверждённой позиции бота формируется отдельный запрос аварийного выхода `PROTECTION_UNCONFIRMED`. Перед исполнением повторно проверяются владелец кампании, направление, объём, цена входа и наличие полного SL. Появившийся ручной SL отменяет необходимость выхода.
4. Аварийный выход проходит через сохранённый Execution Door, использует `reduceOnly` и устойчивый идентификатор. Потеря ответа не разрешает повторную отправку. Подтверждение требует биржевого исполнения и проверки позиции.
5. Перед выходом проверяется отмена остатков входа и добавлений. Для сработавшей условной заявки проверяется её фактическая дочерняя заявка `actualOrderId`.
6. Статус исполненного входа обновляется по биржевому исполнению, даже если заявка уже исчезла из списка открытых. Это исключает фиктивное ожидание отмены `NEW` после исполнения.
7. Если общий аудит прерван, дополнительная проверка может запросить защитный выход только по исполнению, заново подтверждённому в текущей сверке, с совпадающими количеством и ценой позиции. Позиция без доказанного владельца автоматически не закрывается.
8. Восстановление суточной базы риска по подписанным REST-данным больше не зависит от успешного согласования принадлежности заявок и синхронизации приватного потока. Независимые ограничения новых входов сохраняются.
9. Синхронизация приватного потока различает подтверждённый снимок счёта и разрешение торговать. Полный анализ десяти пар сохраняет состояние `READY_BLOCKED`, когда исполнение заблокировано.
10. Диагностика экспортирует параметры наблюдаемых стопов и внешних заявок, свежесть доказательств и принадлежность стратегии. Неизмеренный риск передаётся как неизвестный, а не как ноль. Подтверждённый ручной SL не означает готовность автоматического сопровождения.
11. Неполный Gradle wrapper заменён официальным wrapper 8.14.6. Проверены его SHA-256 и контрольная сумма дистрибутива.

## Проверка

Проверки выполняются локально на воспроизводимой модели биржи с реальным координатором и подписанным транспортом; сетевой собеседник моделируется.

- Python: 914 passed, 2 skipped; предупреждения FastAPI о старом lifecycle API остаются отдельным техническим долгом.
- Android: 559 JUnit-тестов без ошибок, включая LONG/SHORT, отказ SL, потерю ответа, перезапуск координатора, ручной SL и частичное исполнение.
- Обязательны `:app:testDebugUnitTest`, `:app:lintDebug`, `:app:assembleDebug`, `ci_release_gate.py` и проверка подписи APK.

## Границы подтверждения

Модель не заменяет приёмку на телефоне с Binance Futures Demo. Нельзя считать подтверждёнными реальные параметры конкретного стопа по архиву без полного биржевого ответа. Изменения не доказывают полного соответствия всем книгам Вильямса.

Обновление Android поверх установленного приложения требует совпадения ключа подписи. Локальная тестовая сборка не должна использоваться как повод удалить приложение с действующим журналом исполнения. Ключ предыдущей установленной сборки требуется для обновления с сохранением данных.
