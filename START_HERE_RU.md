# Williams Bot — инструкция для владельца

## 1. Актуальное состояние проекта

Это Android-приложение для автономного наблюдения и торговли на **Binance USDⓈ-M Futures Demo**. Runtime приложения использует Futures Demo API и работает локально на Android. Удалённый Python backend не является обязательным шлюзом исполнения Android-кампаний.

**Версии не смешивать:**
- main в репозитории на момент обновления этой инструкции: **4.64.18**.
- fix/nov16-durable-private-event-inbox-4.64.37: исследовательский кандидат **4.64.37**, ещё не принятый в main.
- Кандидат нельзя считать релизом или доказанно готовым автономным торговым приложением только на основании успешной сборки/эмулятора.

## 2. Рынок и ограничения

- Только **Binance USDⓈ-M Futures Demo** (demo-fapi.binance.com).
- Не Spot Testnet и не основной биржевой Futures API.
- Режим позиции — One-Way; используемая конфигурация маржи — Isolated.
- 15 контрактов входят в перечень сопровождения. Новые сделки разрешены только для утверждённой десятки; не более 10 одновременных кампаний.
- Начальный риск в конфигурации проекта — 0,20%; максимальный риск одного входа — 0,25%; лимит риска кампании/портфеля — 0,60%; дневной лимит потерь — 3%. Не менять эти параметры без отдельного аудита.
- Поддерживаются LONG и SHORT.
- Входные решения принимаются на закрытых H1-свечах; H4 и D1 используются как контекст/фильтр.
- Любое состояние неопределённости, устаревшая сверка или неподтверждённый STOP должно блокировать новые входы.

## 3. Установка Android APK

1. Используйте только APK, собранный workflow **Build Android APK** с постоянным подписывающим сертификатом.
2. Не устанавливайте APK из Campaign CI или локальную сборку с временной debug-подписью поверх существующей установки: Android может отклонить обновление из-за несовпадения сертификата.
3. Сверьте SHA-256 APK с опубликованным checksum.
4. Не удаляйте данные приложения и SQLite-файлы при наличии открытых позиций, ожидающих ордеров или неизвестного результата отправки.

Для исследовательской ветки используйте APK только после успешного CI именно на том commit SHA, из которого он собран. Эмуляторная проверка UI не является Binance Demo E2E-приёмкой.

## 4. Подключение Binance Futures Demo

1. Создайте отдельный API-ключ именно для USDⓈ-M Futures Demo.
2. Оставьте выключенным вывод средств и не предоставляйте ненужные разрешения.
3. Введите API Key и API Secret непосредственно в настройках приложения.
4. Не отправляйте секрет в чат, issue, PR, логи, скриншоты или GitHub.
5. Убедитесь, что приложение показывает Futures Demo, а не Spot и не основной биржевой аккаунт.

Ключи хранятся в защищённом Android-хранилище приложения. При смене API-ключа сначала убедитесь, что он относится к тому же Demo-аккаунту и что текущие позиции/ордера сверены.

## 5. Первый запуск и восстановление

1. Откройте диагностику и проверьте версию приложения, source revision, состояние локального runtime, SQLite и подключения к Binance.
2. Выполните **RECOVER**. Дождитесь завершения подписанной сверки аккаунта, позиций, обычных и algo-ордеров.
3. Проверьте, что каждая фактическая открытая позиция имеет однозначно принадлежащий ей действующий биржевой защитный STOP с правильными symbol, side, quantity/closePosition, trigger price и clientAlgoId.
4. Только после успешной сверки можно рассматривать запуск мониторинга. Сам статус READY на экране не заменяет проверку фактических биржевых данных.

### Если приложение показывает RECONCILE_REQUIRED, UNKNOWN, NOT_VERIFIED или отсутствующий/неоднозначный STOP

- Не пытайтесь повторно отправлять входной ордер.
- Не очищайте SQLite и не удаляйте приложение.
- Не считайте локальную запись FILLED или OPEN_PROTECTED доказательством состояния биржи.
- Сохраните диагностический ZIP.
- Новые входы должны оставаться заблокированными до восстановления точной signed-сверки. Существующие позиции требуют безопасного сопровождения и проверки на Binance Demo.

## 6. Автономная работа Android

Для длительного тестирования:
- разрешите приложению работу без оптимизации батареи в настройках Android/Samsung;
- проверьте foreground service и уведомление о работе;
- отдельно испытайте выключенный экран, Doze, переход Wi-Fi/LTE, отсутствие сети, возврат сети и reboot;
- после каждого сценария проверьте signed позиции и защитные algo-ордера.

Наличие Foreground Service или успешный запуск на эмуляторе само по себе не доказывает, что производитель устройства не остановит процесс.

## 7. Что необходимо до допуска к реальной торговле

Реальные средства запрещены для данного этапа. До отдельного решения о Live должны быть документально приняты:
- подписанные Demo LONG и SHORT полные циклы, включая partial fill;
- точное сопоставление FILLED → биржевой STOP по биржевым ID и измерение задержки;
- отсутствие промежутка без защиты при установке/замене STOP;
- восстановление после потери сети, завершения процесса, reboot и обновления APK на физическом телефоне;
- отсутствие потери/повторного применения private Futures events;
- проверка финансового журнала, дневного лимита и всех риск-резерваций;
- независимая проверка торговых правил по первоисточникам.

**Успешные unit-тесты, CI и эмуляторы не заменяют эти проверки. Этот проект нельзя считать готовым к Live, пока все критические пункты не приняты.**

## 8. Диагностика

В приложении сформируйте полный диагностический ZIP. Передайте архив разработчику без API secrets, паролей, токенов и иных секретов. Диагностика должна включать source revision, версию APK, состояние private stream, очередь/долговечный inbox событий, подписанные снимки позиции и защитных STOP, историю восстановления и причины блокировки.

Не публикуйте публично raw client IDs, account identifiers или приватные журналы без предварительной очистки.
