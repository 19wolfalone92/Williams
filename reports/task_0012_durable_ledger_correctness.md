# TASK 001.2 — Durable ledger correctness
**Status: PARTIAL — P0 OPEN**

## Inspected implementation
- `app/src/main/java/com/williamsbot/DurableMutationLedger.kt`
- `app/src/main/java/com/williamsbot/StandaloneRuntime.kt`
- Existing ledger states: PREPARED, SUBMITTING, UNKNOWN, ACKNOWLEDGED, RECONCILED, REJECTED.
- Intent rows have unique operation IDs and immutable kind/symbol/fingerprint/client ID fields by conflict checking.
- SQLite transitions are transactional and use an expected-state compare-and-update. This helps prevent two ledger instances from both successfully claiming the same PREPARED state, but an end-to-end concurrent network-submission proof has not been run.
- Unresolved states are PREPARED, SUBMITTING, UNKNOWN. Database exceptions must remain blockers; no claim is made that every persistence failure path has been injected and tested.

## TASK 001.2 code correction
Added `MutationIdentity.kt`; `StandaloneRuntime.signedRequest()` now derives a generated client order ID deterministically from method, path, symbol and the unsigned request parameters rather than generating a fresh UUID for this fallback. The helper hashes unsigned operation input only; credentials, timestamp and signature are not part of the seed. The fingerprint uses SHA-256 through the same helper.

## Remaining correctness gaps
- Existing caller-provided IDs can still be generated by call sites using time-based/random values; a caller-supplied durable operation context is not required at the sink.
- Same logical request with different parameter ordering may produce a different fallback identity.
- No normalized durable record exists for both legs of cancel-replace or complete exchange observations.
- Schema migration, storage corruption and response-persistence failure coverage are incomplete.
- Tests for the helper were added but have not been observed executing in CI after TASK 001.2 edits.

Do not treat this report as proof of complete durable operation safety.
