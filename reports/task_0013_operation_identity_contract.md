# TASK 001.3 — Operation identity contract

**Status: PARTIAL — P0 OPEN.** Implementation/test source SHA: `8415ab5e6b74e082b865e2cf2ddbcbde29fdb366`.

## Implemented
- `MutationIdentity.kt` contains `LogicalMutationIdentity`, separating logical operation identity from network attempt identity and representing operation type, campaign/signal references, exchange, symbol, mutation type, canonical fingerprint, state, client IDs, timestamp and attempt ID.
- Unsigned form parameters are percent-decoded, sorted by exact parameter name, then deterministically encoded.
- Symbol and enumerated values are normalized; known decimal fields use `BigDecimal.stripTrailingZeros().toPlainString()`.
- `timestamp` and `recvWindow` are excluded as transport metadata. Duplicate parameters and signature/API-key/secret/authorization fields are rejected.
- `StandaloneRuntime.signedRequest()` uses canonical fingerprints and typed operation-ID construction. It fails closed if a mutation has no stable client/target key instead of creating a fresh random UUID fallback.
- Client IDs generated by the explicit logical-operation overload are 32 characters with `W21_` prefix and distinguish identical economic parameters when operation IDs differ.

## Remaining blockers
The typed model is not yet fully supplied from every caller; most existing ledger writes leave campaign/signal fields null. The SQLite schema now persists exchange, optional campaign/signal IDs, a stable first-attempt ID and timestamps, but it does not store a history of multiple execution attempts. The legacy four-argument client-ID helper remains request-derived; callers must supply a stable client ID or logical context for genuinely distinct identical requests. Gate A remains **PARTIAL**.
